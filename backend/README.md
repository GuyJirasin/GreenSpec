# GREEN SPEC workflow backend (local development)

This is the new standalone workflow backend. The original Python/AI engine is a read-only reference and is not called. Results use controlled, versioned fixtures with a visible `simulated` provenance label. Arbitrary uploads are retained privately but cannot receive fabricated analysis or revision output.

## Start with Supabase local

Prerequisites: Node.js 22+, Docker Desktop with its engine running. Docker was **not installed** during implementation because the user requested code/setup preparation only. No cloud resources were provisioned or deployed.

Run from this `backend` directory:

```powershell
npm ci
npx supabase start
npx supabase db reset
npm run functions
```

The local API is `http://127.0.0.1:54321`; PostgreSQL is port 54322; Studio is `http://127.0.0.1:54323`; the local email inbox is `http://127.0.0.1:54324`. Read the publishable/anon key from `npx supabase status` and put it in **frontend/.env.local** with `VITE_SUPABASE_URL`. Never put a service-role key in frontend configuration. Auth verification is enabled: register in the UI, open the verification email in the local inbox, then sign in. Password-reset links use the same inbox. Local credentials are generated by Supabase CLI, not committed here.

Functions use generated copies of the canonical shared modules inside `supabase/functions/_shared/domain`, so every import stays inside the Edge runtime mount. `npm run functions` synchronizes these copies and their SHA-256 manifest before starting the server. Committed copies also support direct `npx supabase functions serve`; resynchronize after changing shared modules. Tests check byte parity with canonical sources. This keeps the provider adapter separate from persisted workflow rules.

## API contract

Reads use Supabase tables with membership RLS. All authenticated domain writes use RPCs, while the server worker alone can commit checked uploads, analysis results and revision outputs. The frontend uses the following operations:

| Operation | RPC / Edge function |
|---|---|
| Create project | `gs_create_project(p_name,p_description)` |
| Versioned save | `gs_mutate(p_project_id,p_kind,p_id,p_expected_version,p_data,p_request_id)` |
| Member add/change | `gs_member(p_project_id,p_email,p_role,p_remove)` |
| Member removal by ID | `gs_remove_member(p_project_id,p_user_id)` |
| Archive/restore | `gs_archive(p_project_id,p_archived,p_expected_version)` |
| Analyze/iterate | Edge `analyze`: project_id, request_id, scenario, document_version_ids[], parent_run_id?, feedback? |
| Finalize | `gs_finalize(p_run_id,p_review_epoch,p_request_id,p_omit_errors,p_omission_reason)` |
| Reopen | `gs_reopen(p_decision_set_id,p_request_id)` |
| Explicit PM handoff | `gs_handoff(p_decision_set_id,p_item_ids,p_request_id,p_replace_reason)` |
| Verify | `gs_verify(p_package_id,p_result,p_notes,p_evidence_ids)` |
| Generate fixture revision | Edge `revision`: decision_set_id, request_id |
| Approve revision | `gs_approve_revision(p_revision_id,p_expected_version,p_exclusions)` |
| In-app alerts | `gs_evaluate_notifications(p_project_id)`, `gs_mark_notification(p_id)` |
| Abandoned job/upload recovery | `gs_recover_jobs(p_project_id)` |

`gs_mutate` supports projects, documents, reviews, feedback, package owner assignment, tasks, milestones, procurements, implementation_entries, issues, actual_results and comments. Document versions, recommendations, snapshots, activity and system status flags cannot be written directly by a browser. An optimistic conflict returns `VERSION_CONFLICT` and the current row in the error detail; a caller must reload or explicitly reapply, never blindly overwrite.

The Edge `document` function supports:

- `fixture`: project_id, fixture_id, request_id. Creates a source document and uploads exact bytes/checksum/locators from the shared fixture manifest. Call once for every selected scenario fixture ID.
- `begin`: project_id, document_id **or** package_id, filename, mime, bytes, request_id, optional evidence_kind. Returns id/storage_path; upload bytes using Supabase Storage bucket `documents` or `evidence`.
- `commit`: project_id, version_id **or** evidence_id, checksum. Server downloads the actual bytes, checks size/signature/SHA-256, then marks the exact version READY. Arbitrary uploads remain provenance `uploaded`; the browser cannot assign a fixture ID.
- `cancel`: version_id or evidence_id. Retains a failed draft for retry; no hard-delete operation.

Storage signed download URLs should expire in 300 seconds. Client uploads are permitted only to previously registered UPLOADING paths belonging to an active editing member. Client overwrites and deletes have no policy. Every referenced ready source version remains immutable, including retired documents and historical decisions.

## Behavior and boundaries

Finalize freezes persisted reviewed recommendations, forbids unresolved/overlapping approved scopes and stale inputs, and records explicit partial-source omissions and numeric coverage. Handoff is serialized per project, idempotent per request/item/scope, and never runs on approve. An unchanged decision returns its existing package. Replacing an untouched package requires a reason; changed started execution returns a committed `EXECUTION_STARTED` result with a review issue, creating no packages in that transaction. Historical superseded packages stay readable.

Delivery/install corrections append an event referencing the old entry. Installation cannot exceed delivery. Verification requires quantity coverage, ready evidence, reviewer and notes, with no open blocking issue. Latest nonconformance or a new blocking issue removes COMPLETE. Actuals are separate totals with units/method/source/provenance; missing values stay null and cannot be replaced with estimates.

Revision generation records REQUESTED/GENERATING/READY_FOR_REVIEW/PARTIAL/FAILED, writes a separate output version and before/after/unapplied report, and checks original SHA-256. Only exact approved fixture DOCX paragraph edits are supported. Approval records exclusions/reasons and cannot approve an outdated output. Originals are never overwritten.

Notifications run on relevant RPC mutations and, where pg_cron is available, at 00:00 Asia/Bangkok each day. Dedup keys use the Bangkok calendar date. No email/SMS is sent. Archive suppresses evaluation and product writes. Auth/member roles are owner/editor/viewer, with last-owner protection and same-project FK checks.

## Verification

The parent `qa/backend.test.mjs` runs migrations/functions in actual embedded PostgreSQL (PGlite) with deliberately stubbed Auth/Storage schemas and identities. It checks RLS, permission denial, snapshots, conflicts, idempotency, reconciliation, installation/verification and notification behavior. `qa/backend-storage.test.mjs`, when present, covers registered object path policies. Run from `qa` with its documented command. These tests do **not** prove Supabase Auth email delivery, Docker runtime, object-store transfer or Edge deployment integration.

After Docker is available, perform the full local integration checks in `INTEGRATION_CHECKLIST.md`. No claim of a running local Supabase service or production readiness is made by the code alone.
